# Asyra Runtime Atlas Plan

## Status

Required child plan of the
[Asyra Framework Website Program](asyra-framework-website-plan.md). The Atlas
is a real-runtime product surface, not a decorative architecture diagram.

Implementation begins only after approved executable examples, visual
reimagine, common site platform, an exact Atlas Inspector, executable runtime
cases, observation contracts, and bounded Definition of Done are ready.

## Goal

Let visitors operate and inspect the real public Asyra runtime while seeing
intent, ownership, transaction, canonical state, projection, optional
composition, and failure evidence. The Atlas must demonstrate that canonical
information modeling can be visual, headless, or both.

## Ownership Boundary

This plan owns `/atlas`, any bounded Landing Atlas adapter, Atlas runtime
composition, observation/evidence adapters, controls, state visualization, and
its six required executable cases.

It does not own Framework behavior, package tests, public documentation prose,
general website foundations, example source semantics, app domain policy,
Asyra Design behavior, or production deployment.

Atlas observations must come from public Framework paths or formally owned
diagnostic evidence. It may not infer correctness from rendered pixels, invent
fallback state, or import package-private internals.

## Required Runtime Evidence

Visitors must be able to inspect:

- intent source and Feature/session routing;
- public App/Core API calls;
- transaction start, updates, commit, rollback, and one intended Undo unit;
- canonical Props, Scene Tree, Selection, and System Context ownership;
- optional Render/UI Context, serialization, search/index, and downstream or
  app-owned consumers;
- Preset defaults and app-owned replacements;
- optional Collaboration and AI composition with inert-disabled behavior; and
- package, artifact, bypass, and failure ownership at each step.

## Required First-Release Cases

1. A continuous pointer interaction with multiple visible updates and one Undo
   commit.
2. One canonical state change projecting to canvas, hierarchy, properties, and
   serialized data.
3. Invalid input rejection or transaction rollback without partial canonical
   state.
4. Two in-browser actors using explicitly composed non-durable reference
   Collaboration.
5. A deterministic prepared AI action executing only through registered
   app-owned actions and the ordinary transaction path.
6. A headless information model with no Render or UI dependency, queried
   through app-owned retrieval/index logic and mutated only through registered
   Feature/API boundaries.

The first visual case may use design-tool geometry, but domain-specific BIM,
VR, physics, chemistry, simulation, AI retrieval, and action policy remain
app-owned and must not be fabricated as Framework output.

## Interaction Contract

Hover, keyboard focus, touch selection, and reduced-motion navigation must
reveal equivalent owner, input, output, condition, bypass, and example-package
information. AI, Collaboration, Provider, Render, and UI must never appear as
canonical document owners.

Users must be able to replay, pause, step, reset, and compare relevant cases
without creating ambiguous hidden state. Each case has deterministic initial
state, action sequence, evidence record, expected result, and failure state.

## Example and Platform Handoff

Atlas cases may adapt the maintained executable examples only through a
verified browser/runtime adapter. Any necessary behavioral variant becomes an
owned tested case rather than an inline fork.

The site platform supplies shared navigation, visual primitives, focus/error
foundations, and content links. The Atlas owns only runtime-specific
interaction and evidence.

## Implementation Stages

1. Freeze Atlas case schemas, observation model, public API boundary, and
   Inspector.
2. Prove the headless and canonical-state cases outside presentation.
3. Prove transaction, rollback, projection, Collaboration, and AI cases.
4. Implement deterministic replay, stepping, reset, and evidence views.
5. Apply the accepted responsive visual and motion specification.
6. Integrate the bounded Landing adapter without duplicating runtime logic.
7. Run runtime, failure, accessibility, responsive, performance, and
   synchronized visual gates.

## Quality Gates

- all displayed evidence derives from the real public execution path;
- case results match formal expected canonical state and transaction behavior;
- rollback leaves no partial canonical state and continuous input creates one
  intended Undo unit;
- optional systems are explicitly composed and inert when disabled;
- the headless case imports and requires no Render/UI package;
- AI actions use registered app-owned actions and ordinary permission and
  transaction boundaries;
- keyboard, touch, focus, replay, reset, reduced-motion, and responsive cases
  pass;
- runtime and rendering performance budgets pass; and
- visual review inspects default, active, success, failure, and headless states.

## Stop Conditions

- Evidence requires package-private imports or inferred/fake state.
- A case conflicts with active Framework contracts or formal tests.
- An app-owned domain rule is presented as Framework output.
- Atlas implementation would become a second canonical state owner.
- A case requires an unapproved dependency or unverified package artifact.
- A required runtime, accessibility, performance, or visual gate fails.

## Definition of Done

- All six cases execute deterministically through public Framework boundaries.
- Visitors can inspect exact intent, transaction, canonical owner, projection,
  optional-system, bypass, and failure evidence.
- The headless case proves canonical behavior without Render/UI or a visible
  product surface.
- Atlas interactions are responsive, accessible, performant, and visually
  accepted.
- `/atlas` and its bounded Landing adapter are Preview-ready without claiming
  production deployment.
