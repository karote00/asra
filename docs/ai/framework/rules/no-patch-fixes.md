# Rule: No Patch Fixes

## Scope

This rule applies to the whole project: framework packages, preset defaults,
reference apps, future apps, generated app templates, inspectors, visual review
flows, export paths, hit testing, and diagnostics that can influence product
output.

## Core Rule

Do not fix a product bug by adding patch geometry, patch state, patch routing, or
one-off special-case output that hides an incorrect upstream algorithm.

A fix must repair the canonical data flow, ownership model, product pipeline, or
contract that produced the wrong behavior. The same source semantics must then
produce correct product output through the normal path.

## Forbidden Patterns

- Adding extra render polygons, masks, caps, joins, hit regions, export shapes,
  or final-face entries only to cover a visible defect while leaving the
  canonical interval/domain/ownership logic wrong.
- Adding fixture-specific, vector-specific, app-specific, or inspector-specific
  branches for a general framework behavior.
- Reinterpreting debug metadata, visual probes, or inspector data as product
  input.
- Suppressing a failing product path and replacing it with a later fallback
  product path.
- Fixing only the final renderer/exporter when the defect originates in source
  modeling, domain planning, interval allocation, ownership assignment, or
  materialization contracts.
- Encoding user-reported screenshots as hardcoded coordinates, tolerances, or
  scenario-specific exceptions.

## Required Handling

When a behavior is wrong:

1. Identify the first stage where the canonical semantic contract becomes
   incorrect.
2. Fix that owner stage, not a later visual/product symptom.
3. Preserve provenance through downstream stages so tests can prove the product
   came from the intended semantic owner.
4. Add regression tests at the failing semantic boundary and at the final product
   boundary.
5. For visual behavior, run app visual review after unit/integration tests pass;
   do not use app screenshots as the definition source.
6. Update framework and app docs when the rule or product contract changes.

## Allowed Non-product Uses

The following are allowed only when they are isolated from product output and
named as diagnostics, tests, or oracles:

- Visual markers used to explain failures.
- Unit-test geometry oracles.
- Inspector overlays that display expected vs actual behavior.
- Temporary investigation code that is not committed.

These artifacts must not be consumed by runtime product rendering, export,
hit testing, persisted model data, or app behavior.

## Review Checklist

Before claiming a fix is complete:

- [ ] the first incorrect semantic stage has been identified
- [ ] no product output is generated by a patch/fallback path
- [ ] no fixture-specific branch is required for the general behavior
- [ ] product metadata still traces to the canonical owner
- [ ] tests fail without the semantic fix and pass through the normal pipeline
- [ ] app visual review has been run for visual changes, when applicable

## Relationship to Other Rules

This rule extends `pre-release-legacy-removal.md`: a patch path is a stale
alternate product path unless it is isolated as a non-product diagnostic.

This rule also applies to all app contexts under `docs/ai/apps/*`. App-level
code may narrow product behavior, but it must not bypass framework contracts
with patch output.
