# Rule: Pre-release Legacy Removal

## Scope

This rule applies to any framework, preset, or app behavior that has not been released as a public compatibility contract.

Released public APIs follow `deprecation-lifecycle.md`. Unreleased internal flows, product render paths, app workflows, debug metadata, and migration experiments do not get a compatibility window.

## Core Rule

Pre-release legacy code must be upgraded to the current contract or deleted. It must not remain reachable as a product path, hidden fallback, alternate data shape, or diagnostic-driven runtime branch.

## Forbidden Patterns

- keeping an old implementation as a "safety fallback" after a new product contract exists
- routing visible render, hit-test, export, undo/redo, or data-channel behavior through legacy branches
- keeping multiple runtime meanings for one model field after the canonical data format is defined
- accepting old internal metadata as an active runtime signal instead of migrating it at the load boundary
- adding compatibility flags for unreleased behavior to avoid removing stale branches
- making diagnostics, probes, helper geometry, or fallback artifacts drive product output
- fixing only the crash site while leaving equivalent legacy reads or conditions elsewhere

## Required Handling

When a change replaces an unreleased behavior:

1. Identify every previous entry point, helper condition, cache key, fallback, and debug/probe path that can still reach the old behavior.
2. Delete unreachable or incorrect old paths in the same change.
3. Move necessary old-data handling to an explicit load-time migration or validation adapter.
4. Name any remaining non-product path as `diagnostic`, `unsupported`, or `load-migration`; never name it as fallback product behavior.
5. Add tests that prove the legacy path is not reachable from the product flow.
6. Update docs and inspector/plan contracts so future work cannot cite the stale rule as active guidance.

## Allowed Exceptions

The only allowed legacy handling for unreleased behavior is:

- load-time migration from an old saved shape into the current canonical shape
- tests that assert old product paths are removed or unreachable
- diagnostics that describe why a path is unsupported, without producing product output
- temporary investigation code that is not committed

Any exception must be isolated from runtime product output and named as such.

## Review Checklist

Before claiming a bug fix, refactor, or performance change is complete:

- [ ] no product path still branches on the removed rule
- [ ] no visible output can be produced by the old helper/fallback
- [ ] no cache key can reuse product data generated by the old rule
- [ ] no data-channel subscriber depends on the old payload shape
- [ ] no docs, active plans, or inspector flow describe the old rule as current
- [ ] regression tests cover both the new behavior and non-reachability of the old behavior

## Relationship to Fallback Semantics

Load validation fallback is still required for invalid persisted data. That fallback must normalize data before it enters runtime stores.

Runtime product fallback is not allowed when it changes semantics, hides unsupported behavior, or competes with the current product contract.
