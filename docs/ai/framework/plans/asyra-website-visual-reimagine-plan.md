# Asyra Website Visual Reimagine Plan

## Status

Queued child plan of the
[Asyra Framework Website Program](asyra-framework-website-plan.md). This plan
must complete before Landing, documentation shell, Runtime Atlas, or any other
major composed view begins implementation.

The reimagine segment requires its own visual-experience contract, exact flow
Inspector, required view-state cases, and formal visual inspection. The user's
later program instruction removes the intermediate manual checkpoint: the
accepted handoff is frozen autonomously and remains subject to the user's final
integrated-goal acceptance.

## Goal

Create an original visual, interaction, and motion language from Asyra's
architecture and future direction before translating it into website code.
The result must feel native to Asyra rather than like a generic documentation
template with substituted colors.

The audience is global and not limited to engineers. The primary narrative
must let a non-engineer understand what Asyra enables, what the App creator
owns, and why deterministic composition matters before encountering package,
transaction, or runtime vocabulary. Technical depth remains available through
progressive disclosure rather than becoming the price of entry.

## Ownership Boundary

This plan owns concept images, annotated visual decisions, responsive states,
motion storyboards, semantic visual roles, and the accepted implementation
specification. It does not own product claims, documentation semantics,
website components, production assets, or Runtime behavior.

Generated images are design evidence, not semantic authority and not automatic
production assets. Any external asset, font, or licensed media requires an
explicit ownership and approval decision before implementation.

## Required Reimagine Set

Image generation must produce and inspect multiple coherent directions, with
at least:

- desktop Landing page;
- mobile Landing page;
- desktop documentation page;
- mobile documentation navigation and reading state;
- Runtime Atlas default state;
- Runtime Atlas active-flow and failure states;
- Asyra Design case-study presentation;
- release or roadmap boundary state; and
- key motion and transition storyboard frames.

At least one direction must prove long-form reading quality, responsive intent,
keyboard/focus visibility, reduced-motion equivalence, and feasible production
translation rather than only a dramatic hero image.

The frozen view-state ids are:

- `landing-desktop` and `landing-mobile`;
- `docs-desktop`, `docs-mobile-navigation`, and `docs-mobile-reading`;
- `atlas-default`, `atlas-active-flow`, and `atlas-failure`;
- `asyra-design-case-study`;
- `release-roadmap-boundary`; and
- `motion-intent`, `motion-transaction`, `motion-projection`, and
  `motion-reduced`.

Composite boards may contain multiple ids only when each state remains legible
at useful inspection scale. The reimagine must retain three distinct concept
directions before selecting one implementation direction.

## Visual Language Contract

- Dark-first identity may be used, but long-form docs require an accessible
  light or high-contrast reading strategy when dark presentation harms
  readability.
- Avoid interchangeable shadcn/Vercel/Supabase card grids, default emerald
  gradients, and decorative architecture diagrams.
- Nodes represent canonical owners or registered capabilities.
- Edges represent intent, events, relations, apply paths, or projections.
- Brackets represent transaction boundaries.
- Layers distinguish Framework, Preset, App, Provider, and product UI.
- Solid, dashed, and muted routes distinguish canonical, optional, and bypassed
  paths.
- Color roles remain semantically consistent across Landing, Atlas, diagrams,
  code annotations, and documentation callouts.
- Canvas-plane depth, coordinates, topology, and state transitions provide
  functional structure rather than decoration.
- Typography prioritizes reading while retaining a technical monospace voice
  for code, owner labels, transaction state, and runtime evidence.

## Global Audience Contract

- Above-the-fold value language uses plain international English and concrete
  outcomes; it does not require programming vocabulary, regional idioms, or
  prior knowledge of canvases and runtimes.
- Product possibilities such as whiteboards, BIM, VR, industrial simulation,
  AI-facing information products, and unforeseen domains are shown as examples
  of what an App may build, never built-in promises.
- The first layer explains `you define the knowledge and product`; the second
  explains `Asyra keeps actions, ownership, and outcomes predictable`; deeper
  layers expose packages, transactions, providers, and evidence.
- Layouts tolerate longer localized strings, preserve logical reading order,
  and never encode meaning by color alone.
- The technical visual language remains available to engineers without making
  the non-engineer path a simplified or lesser experience.

## Motion Contract

Motion may trace intent, open and close a transaction bracket, pulse an active
canonical owner, fan out projections, or reveal optional composition. Every
motion must be purposeful, inexpensive, cancellable where applicable,
keyboard-equivalent, and represented by a clear reduced-motion state.

The storyboard must define trigger, duration class, state change, semantic
meaning, focus behavior, interruption behavior, and reduced-motion result. It
must not prescribe animation that hides content correctness or delays ordinary
navigation.

## Implementation Handoff

The accepted direction must specify:

- responsive layout and composition rules;
- typography scale and reading measure;
- color, border, depth, and state roles;
- spacing and density rules;
- shared component anatomy without prematurely coding components;
- interaction, hover, focus, active, empty, loading, failure, and disabled
  states;
- motion tokens and reduced-motion equivalents; and
- per-view annotations explaining which visual marks carry semantic meaning.

The retained project evidence lives under
`docs/ai/framework/website/visual-reimagine/`. `concept-manifest.json` owns the
exact direction, selected-board, view-state, prompt, and inspection inventory;
`handoff.md` owns the annotated implementation contract. Generated images are
not production assets and never replace those semantic records.

## Autonomous Inspection And Final Acceptance

The Visual Reimagine child does not pause for an intermediate human checkpoint.
Every generated board is inspected at full image scale; the retained direction
must pass originality, hierarchy, responsive, reading, semantic-role,
accessibility, reduced-motion, and implementation-feasibility checks. The
selected handoff then becomes the fixed input for Website Platform, Landing,
and Runtime Atlas implementation. The user performs one final acceptance after
the integrated program goal is complete.

## Deferred Image-Only Alternate Reimage

After the implemented website and launch work are complete, generate one
coherent second visual version for the user to explore. This final alternate
set is image-only: it does not reopen the accepted handoff, mutate website
code, change production assets, or trigger another implementation cycle. It
must be materially different in composition and art direction rather than a
palette swap.

## Stages

1. Freeze the visual brief from the accepted product/content contracts.
2. Generate multiple full-page directions and required states.
3. Inspect originality, hierarchy, readability, responsive intent,
   accessibility risk, semantic accuracy, and implementation feasibility.
4. Select and refine one coherent direction.
5. Produce annotated responsive and motion specifications.
6. Freeze the selected direction through formal autonomous visual inspection.
7. Freeze the accepted handoff for platform, Landing, and Atlas tasks.

## Quality Gates

- every required view/state is represented at useful inspection scale;
- the first narrative layer is understandable without engineering knowledge
  and the technical layer remains available through progressive disclosure;
- visual roles do not imply incorrect Framework ownership;
- current visual, future non-visible, and optional paths remain legible without
  collapsing roadmap work into current support;
- mobile and long-form reading are first-class;
- focus, contrast, reduced motion, touch targets, and failure states have an
  explicit feasible solution;
- implementation does not require unapproved assets or dependencies; and
- one exact annotated direction has passed the formal visual handoff gate and
  is reserved for final integrated-goal acceptance.

## Stop Conditions

- Product/content meaning is not stable enough to visualize.
- A direction relies on a generic template rather than Asyra semantics.
- The concepts omit mobile, documentation, Atlas, failure, or reduced-motion
  states.
- Visual choices imply Render/UI are required for canonical behavior.
- Implementation would require an unapproved external asset or toolchain.
- Formal inspection cannot select one direction without an unresolved semantic
  or implementation-feasibility conflict.

## Definition of Done

- One coherent image-first direction is formally selected for all required
  surfaces and reserved for final integrated-goal acceptance.
- Responsive, interaction, motion, accessibility, and semantic roles are
  annotated precisely enough for implementation.
- Landing, platform, and Atlas tasks can consume the same frozen design
  language without inventing independent styles.
- Post-implementation synchronized visual review has a concrete accepted
  reference set.
- The deferred second visual version is delivered as images only after the
  integrated website is complete.
